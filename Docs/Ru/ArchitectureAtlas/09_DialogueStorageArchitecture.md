# Dialogue Storage Architecture

> Version: 1.0
> Last Updated: 15-07-2026

---

# Purpose

Определить единую архитектуру хранения диалогов проекта.

Система ориентирована на сюжетную RPG / Visual Novel, где большинство диалогов являются линейными, а нелинейность реализуется через отдельные точки выбора.

Архитектура должна поддерживать постепенное развитие проекта без переписывания игровой системы.

---

# Architecture Name

**Node-Based Dialogue Architecture**

Excel → JSON pipeline with ID-linked dialogue nodes, designed for incremental evolution from linear narratives to complex RPG dialogue systems.

---

# General Concept

Диалоги создаются в Excel.

Excel является единственным источником данных (Source of Truth).

Во время сборки или импорта данные автоматически конвертируются в JSON.

Во время выполнения игры используется исключительно JSON.

```
Excel
        ↓
 Dialogue Converter
        ↓
     JSON Files
        ↓
 Dialogue Runtime
```

---

# Design Goals

Система должна:

- быть удобной для сценаристов;
- поддерживать большие объемы текста;
- легко храниться в Git;
- поддерживать линейные диалоги;
- поддерживать локальные ветвления;
- иметь возможность развития без изменения архитектуры.

---

# Core Principle

Диалог представляет собой набор связанных между собой узлов (Dialogue Nodes).

Каждый узел имеет уникальный идентификатор (ID).

Связь между узлами осуществляется исключительно через ID.

Даже полностью линейный диалог рассматривается как последовательность связанных узлов.

---

# Dialogue Structure

Базовый сценарий выглядит как линейная цепочка.

```
1
↓

2
↓

3
↓

4
↓

5
```

Если явно не указано иное, переход осуществляется к следующему узлу.

---

# Branching Model

Ветвления являются локальными.

```
          Choice

         /      \

       30        50

         \      /

          80
```

Переходы всегда выполняются по ID.

Диалог не рассматривается как дерево.

Он рассматривается как граф узлов.

---

# Source of Truth

Редактирование выполняется исключительно в Excel.

JSON никогда не изменяется вручную.

---

# Converter Responsibilities

Конвертер обязан:

- читать Excel;
- выполнять преобразование в JSON;
- выполнять валидацию;
- сообщать обо всех ошибках.

---

# Validation

Минимальная проверка включает:

- уникальность ID;
- существование Target ID;
- отсутствие битых ссылок;
- корректность структуры данных.

При наличии ошибок JSON не создается.

---

# Scalability

По мере роста проекта допускается разделение диалогов:

- по главам;
- по персонажам;
- по локациям;
- по квестам.

Это не влияет на игровую систему.

---

# Future Evolution

Архитектура изначально проектируется как расширяемая.

По мере развития проекта могут добавляться новые свойства узлов.

Например:

- выборы;
- условия;
- игровые переменные;
- проверки навыков;
- последствия выбора;
- запуск событий;
- изменение состояний мира;
- анимации;
- управление камерой;
- управление музыкой;
- управление озвучкой;
- внутренние монологи;
- скрытые варианты ответа;
- локализация;
- пользовательские типы узлов.

Расширение структуры узла не должно требовать изменения общей архитектуры хранения данных.

---

# Editor Evolution

На ранних этапах используется Excel.

При необходимости редактор может быть заменен:

```
Excel

↓

Excel + Validation

↓

Excel + Unity Tools

↓

Dedicated Dialogue Editor

↓

Graph Editor
```

Замена редактора не должна требовать изменения Runtime или формата хранения данных.

Меняется только способ создания контента.

---

# Long-Term Vision

Даже при переходе к сложной RPG-системе (например, с большим количеством условий, проверок навыков и внутренних состояний персонажей) архитектура остается прежней.

Диалог продолжает представлять собой граф связанных между собой узлов.

Меняется только объем данных, содержащихся внутри каждого узла.

---

# Summary

Выбранная архитектура:

**Node-Based Dialogue Architecture**

```
Excel

↓

Converter

↓

JSON

↓

Dialogue Runtime
```

Основные преимущества:

- простой процесс написания сценариев;
- удобство работы сценаристов;
- хорошая интеграция с Git;
- автоматическая проверка данных;
- простое масштабирование;
- возможность постепенного развития без переписывания существующей системы.
